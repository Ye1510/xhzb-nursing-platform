# 用 AI 工具开发

[← 返回 README](../README.md)

> **先区分清楚**：本页讲的是**开发过程中如何使用 AI 编程工具**（Claude Code 等）。
> 项目**自身的大模型能力**（RAG 问答、AI 健康评估）在 [AI 能力](ai-features.md) 那一页。两者不是一回事。

## 为什么要把这件事单独写一篇

用 AI 写代码本身不难，难的是**让 AI 产出的代码符合本项目约定**。默认状态下 AI 会按它见过的通用 RuoYi 项目习惯写，而本项目的分层、命名、返回结构、Mapper 组织方式都有自己的约定。不解决这个问题，AI 生成的东西每次都要人工大改，反而更慢——因为还得逐行核对它有没有自作主张。

这篇记录的是怎么把这件事工程化。

---

## 一、项目级上下文：`CLAUDE.md`

仓库根目录的 [`CLAUDE.md`](../CLAUDE.md) 是给 AI 看的项目说明书。每次新开对话，AI 自动读取它，不需要我逐条复述背景。

里面写的内容都是**AI 反复问错、或者反复猜错的地方**：

| 章节 | 解决的问题 |
| --- | --- |
| Build & Run Commands | AI 不知道主类在哪、前端怎么起，每次都要翻文件 |
| Module Architecture | 8 个模块各管什么，避免把业务代码写进 `xhzb-common` |
| Backend Layered Architecture | 四层结构与包路径，避免生成扁平结构 |
| Controller / Mapper 约定 | 返回 `AjaxResult`、列表前调 `startPage()`、复杂查询写进 XML |
| Database | 库名、ORM、分页器、关键业务表清单 |
| Huawei Cloud IoT Integration | IoT 客户端在哪个模块、凭证从哪读、产品列表缓存 key |
| Spring AI Integration | 两个 ChatClient 的用途差异、RAG 参数、双 Redis 实例地址 |

**它不是文档的重复，而是"约束的显式化"**。写进 `CLAUDE.md` 的每一条，都对应一个 AI 曾经写错过的点。

## 二、人机分工边界

| 交给 AI | 由人工负责 |
| --- | --- |
| 按既有分层生成 Controller / Service / Mapper / Entity 骨架 | 业务规则本身——护理等级的判定逻辑、报警的阈值口径 |
| 样板代码：DTO/VO 转换、参数校验注解、Swagger 注解 | 权限标识的定义与 `@PreAuthorize` 表达式的正确性 |
| 单个方法的实现（给定明确的输入输出与边界） | 事务边界——哪几步必须在同一个事务里 |
| 报错定位与日志排查 | SQL 审查——索引是否命中、是否有 N+1 |
| 补注释、补文档、写 README | 跨模块改动的判断（该放哪个模块） |
| Vue 页面的表格/表单骨架 | 交互细节与业务校验的前端呈现 |

一句话概括：**AI 负责"照约定铺代码"，人工负责"判断这个约定在这个场景对不对"。**

## 三、实际工作流

1. **先定接口契约** —— 按业务写清接口的入参、出参、错误码。契约不清楚时 AI 会自由发挥，返工成本比先想清楚更高。
2. **让 AI 参照同模块已有类生成** —— 明确指定"参照 `NursingProjectController` 的写法"，而不是让它凭空写。这样分层、命名、注解风格自动对齐。
3. **人工审查四项** —— 权限注解、事务边界、SQL、异常处理。这四项出错在运行期才暴露，且不易通过测试覆盖。
4. **联调后回填 `CLAUDE.md`** —— 如果某类问题出现两次以上，就把它写进 `CLAUDE.md`，避免第三次。
5. **不整段接受** —— AI 产物直接进主分支是禁忌；至少过一次人工改写。

## 四、几个具体例子

### 例 1：让 AI 生成业务模块骨架

只说"写个护理任务模块"，AI 可能给出扁平的单层结构，或把实体直接返回给前端。

改进方式：在 `CLAUDE.md` 里把四层结构与返回约定写死，并指定参照模块。之后生成的代码基本可以直接用，只需要补业务规则。

### 例 2：RAG 参数不是拍脑袋定的

`topK=5`、阈值 `0.7`、分块 `500 token` 这组参数是调出来的，不是 AI 给的第一版。AI 会给一个"合理默认值"，但实际用机构知识库测下来，召回率和答案质量需要按数据特点调整。这部分必须人工做，也是被追问时能讲清楚"为什么是这个数"的地方。

### 例 3：报警规则不是简单阈值

最初的设计是"超阈值就报警"，AI 生成出来的也是这样。实际跑起来误报严重——心率瞬时波动就报警。后来才加上「持续周期」和「聚合周期」两个维度。

这类**业务语义层面的问题，AI 不会主动提出来**，因为它不知道现场是什么样。这是人的价值所在。

## 五、踩过的坑

| 坑 | 表现 | 应对 |
| --- | --- | --- |
| 上下文缺失导致风格漂移 | 同一模块里新代码用了不同的返回结构和命名 | 所有生成请求都要求"参照 X 类" |
| AI 自己发明工具类 | 生成了项目里已存在的工具方法，或引入未使用的依赖 | 生成后用 IDE 检查未使用导入，发现重复实现就删 |
| 改动范围失控 | 只要求改一个方法，AI 顺手重构了相邻代码 | 明确约束"只改此方法，不要动其他代码" |
| 幻觉 API | 调用了不存在的方法或参数 | 编译期即暴露，所以**每次生成后必须编译**，不能攒着一起编 |
| 敏感信息进代码 | AI 可能把示例里的真实 key 写进配置 | 项目约定：所有凭证只走环境变量，配置文件里出现明文即拒绝提交 |
